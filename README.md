# Digital Asset Tag Portal

A working MVP of the Digital Asset Tag Portal described in
`Digital_Asset_Tag_Portal_Architecture_MVP.md`: one stable public link per
asset, written to a QR code and an NFC chip, with an anonymous way for a finder
to reach the owner.

The application follows the conventions of the existing LinkTec site in
`/Users/LinkTec/hydraulic` (PHP, MySQL/MariaDB, LAMP, session based auth,
`LINKTEC_SECURE` guard) so that it can run on the same server and the same
domain, while presenting its own interface.

## What is implemented

| Phase | Feature | Status |
|-------|---------|--------|
| 1 | Register, login, logout, dashboard | done |
| 1 | Asset CRUD (create, edit, deactivate), public ID, public tag page, status | done |
| 2 | QR code (PNG + SVG), NFC payload, tag management, tag replacement | done |
| 3 | "I found this", anonymous message, owner inbox and reply, expiry, rate limit | done |
| 4 | Photo upload with re-encoding, EXIF/GPS removal, up to three photos per tag page | done |
| 5 | Six asset types with their own fields, public/private per field | done |

Deliberately out of scope for this version, as agreed in the architecture
document: native apps, payments, RFID infrastructure, BLE/GPS tracking, real
time location, microservices and AI.

## Stack

- PHP 7.4+ (developed and tested on PHP 8.5), no build step, no Composer
  dependency, no framework
- MySQL / MariaDB through PDO, tables prefixed `dat_`
- Own CSS and vanilla JavaScript, so the Content-Security-Policy can stay
  strict (no `unsafe-eval`, no inline script)
- QR codes generated by the bundled encoder in `includes/qrcode.php`; no
  third-party QR service, so tag URLs never leave the installation

## Local development

```bash
# 1. Start the built-in server with the router (pretty URLs for /t/{id})
php -S localhost:8080 router.php

# 2. Open the site
open http://localhost:8080/

# 3. Run the test suite (no database required)
php tests/smoke.php

# 4. Run the same suite plus HTTP checks while the server is running
php tests/smoke.php --http=http://localhost:8080

# 5. Domain layer end to end (register, assets, tags, messages, permissions)
php tests/integration.php

# 6. Design checks in a real browser (overflow, one h1 per page, contrast,
#    button and navigation wrapping) and screenshots for review
node scripts/ui-check.mjs --base=http://localhost:8080
node scripts/screenshot.mjs --base=http://localhost:8080 --out=/tmp/nfc-shots
```

Without a database the pages still render; a banner explains that the MySQL
connection is missing. Everything except registration, login and tag data works
for layout review.

The two browser scripts use an installed Google Chrome through Playwright
(`chrome` channel), so no browser download is needed. `ui-check.mjs` also has a
`--diagnose=/path` mode that lists the elements responsible for a horizontal
overflow.

## Database

```bash
cp .env.example .env      # then edit the credentials
php scripts/migrate.php   # creates the dat_* tables (idempotent)
php scripts/seed-demo.php # optional: demo account and a demo tag (DEMTAG24)
```

The portal stores its tables in the configured schema (`DAT_DB_NAME`) with the
`dat_` prefix, so it can share a database with the existing site without
touching its tables. Verified schema: MySQL 5.7+/MariaDB 10.2+.

## Deploying on the existing domain

The portal is a plain PHP application. Two options:

**Fastest route: use the bundled uploader**, which mirrors the workflow of the
existing LinkTec site (rsync over SSH, credentials in a local
`.vscode/sftp.json`).

```bash
cp .vscode/sftp.example.json .vscode/sftp.json   # once, then fill in host/user/password
SYNC_DRY_RUN=1 ./scripts/deploy-remote.sh        # preview the file list
./scripts/deploy-remote.sh                       # upload
./scripts/deploy-remote.sh ssh "php scripts/migrate.php"    # create the tables
./scripts/deploy-remote.sh ssh "php scripts/seed-demo.php"  # optional demo tag
```

`.vscode/sftp.json` and `.env` are ignored by Git; keep them local. The upload
excludes `.git`, `tests/`, `docker/`, uploaded photos and the browser test
scripts.

The portal is currently live at `https://www.eurohydraulicparts.com/nfc/`, with
the files in `/data/wwwroot/nfc` and the tables in the `visionary_db` schema
(`dat_` prefix). The demo tag page is
`https://www.eurohydraulicparts.com/nfc/t/DEMTAG24`.

Manual alternatives:

1. **Sub-directory** on the current LAMP host, e.g. `https://www.eurohydraulicparts.com/nfc/`.
   Upload the project into `nfc/`, keep `.htaccess` (Apache rewrite for
   `/nfc/t/{publicId}`), and set:

   ```env
   PORTAL_BASE_URL=https://www.eurohydraulicparts.com/nfc
   ```

2. **Sub-domain**, e.g. `https://tags.eurohydraulicparts.com/`, pointing at the
   same server and document root, with the same `.env` change:

   ```env
   PORTAL_BASE_URL=https://tags.eurohydraulicparts.com
   ```

Set `PORTAL_BASE_URL` **before** printing any QR codes or writing any NFC
chips: it is the address that ends up on the physical tags. The public ID and
the link stay valid across moves, so a later change of host only affects newly
written tags.

Checklist for the server:

- PHP with `pdo_mysql`, `mbstring` and `gd` (GD enables PNG output and strips
  EXIF data on upload)
- Write permission for `storage/uploads/` and `logs/`
- `.env` present and not readable from the web (the packaged `.htaccess` files
  block it on Apache; add the equivalent rule on Nginx, see
  `docker/nginx/portal.conf`)
- The rewrite `t/{publicId}` to `t/index.php?id={publicId}` for pretty tag URLs
- HTTPS, because the tag link is typed by hand and scanned by phones

## Security and privacy choices

- Passwords are stored as `password_hash()` hashes only. The existing LinkTec
  user system also keeps a plaintext copy for its admin tooling; this portal
  deliberately does not.
- Public pages are rendered from an explicit projection (`dat_public_asset()`),
  so internal IDs, the owner id and private metadata cannot leak by accident.
- Private fields (VIN, licence plate, serial numbers, service contact) are
  stored but never rendered publicly.
- Anonymous messages are rate limited per IP hash and per asset, protected by a
  honeypot field and a CSRF token, and expire after
  `PORTAL_MESSAGE_RETENTION_DAYS`.
- Uploads are validated by `getimagesize()`, restricted to JPEG/PNG/WebP, then
  re-encoded through GD, which removes EXIF metadata including GPS.
- All state-changing requests use POST with a CSRF token; deletion is a soft
  delete so a printed tag never turns into a naked 404.
- Login failures are logged in `dat_login_logs` with a salted IP hash and
  throttled after ten attempts in fifteen minutes.

Before a commercial launch, complete `docs/imprint.php` and have the privacy
wording reviewed; the page describes the technical behaviour, it is not legal
advice.
